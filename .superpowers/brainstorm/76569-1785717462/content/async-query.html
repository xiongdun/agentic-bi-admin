② 异步大查询 · 设计方案

突破 30s 超时 + 10000 行限制，支持百万级数据查询

核心问题

当前 execute_sql 同步等待（最长 30s 超时，max_rows=10000 限制）。用户跑大表聚合或多年历史数据时，要么超时失败，要么结果被截断。BI 场景里"跑个全年的销售明细"是刚需，但同步阻塞会占用 granian worker，多用户并发时拖垮整个服务。

执行流程
1. 提交查询
POST /sql/run-async → 返回 task_id
SQL 走完整白名单校验 + 行级注入
↓
2. 后台执行
app/core/bgtask.py 接管
asyncio.wait_for 超时 5min（可配）
流式拉取，不一次性载入内存
↓
3. 结果落库
BiQueryTask.result_json + status=success
超过 10 万行只存前 10 万 + 标记截断
↓
4. 前端获取
GET /sql/task/{task_id} → 轮询
或 GET /sql/task/{task_id}/stream → SSE
完成后展示结果 + 支持导出
数据模型 + 状态机
BiQueryTask (新建)
├─ id, tenant_id, created_by
├─ datasource_id
├─ sql_text 来源 SQL
├─ status pending/running/
│               success/failed/canceled
├─ result_json 结果快照
├─ row_count 实际行数
├─ is_truncated 是否截断
├─ error_msg 失败原因
├─ elapsed_ms
└─ expires_at 过期清理时间
状态机
pending → running → success
pending → running → failed
running → canceled（用户主动取消）
过期任务由定时任务清理（7 天）

关键设计决策（需你确认）

设计倾向

  • 任务队列选型：复用 app/core/bgtask.py（进程内 + Redis 锁），不引入 Celery/ARQ。理由：项目已有此能力，BI 大查询并发量不高（单租户几位数），进程内足够；后续若并发上来再升级
  • 超时配置：异步任务 5 分钟（可配 BI_ASYNC_QUERY_TIMEOUT=300），远大于同步的 30s
  • 行数上限：异步查询 max_rows=100000（同步保持 10000），超过则截断并标记
  • 结果存储：落 BiQueryTask.result_json（JSON 字段），7 天后过期清理。大结果不落库，只存元数据 + 提示用户导出
  • 取消机制：用户可取消 running 状态的任务，通过 asyncio.Task.cancel()
  • 前端获取：优先用 SSE（复用项目已有的 sse_starlette），轮询作为降级

风险/限制

  • 进程内任务在 worker 崩溃时丢失 → status 卡在 running，靠心跳检测（5min 无更新标记 failed）
  • 多 worker 下任务可能不在同一进程 → 提交时随机选 worker，结果统一落库所以不影响获取
  • 大结果 JSON 可能很大（10 万行约几十 MB）→ 用 orjson 压缩 + 限制落库大小
  • 内存控制：流式拉取时用 SQLAlchemy stream_results=True，不一次性 fetchall

前端交互

SQL 工作台增加"异步执行"开关（默认关，保持同步快速查询体验）。开启后：

  • 提交后不阻塞，显示任务列表（状态/耗时/行数）
  • 任务完成后自动展示结果，或点击任务查看
  • 支持取消 running 中的任务
  • 历史任务列表（从 BiQueryTask 查，区分于审计日志）
