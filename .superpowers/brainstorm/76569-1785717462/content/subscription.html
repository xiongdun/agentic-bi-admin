④ 定时报表 · 设计方案

按计划自动跑查询/刷新看板，结果推送到邮件/飞书/钉钉

核心问题

当前用户必须手动打开看板/跑查询才能看数据。企业场景里"每周一早上发销售周报"、"每天 9 点推送昨日核心指标"是刚需。没有定时推送，BI 就只是"主动查"工具，覆盖不到"被动接收"场景。

执行流程
1. 定时触发
manifest 声明 PeriodicTask（每分钟检查）
leader_only + Redis 锁，多 worker 去重
↓
2. 匹配订阅
查 BiSubscription（cron 表达式匹配当前时间）
状态=active，next_run_at <= now
↓
3. 执行查询/刷新看板
单图表：跑 sql_text → 渲染图表
看板：并行刷新所有图表 → 拼接
复用 ②异步大查询 的执行引擎
↓
4. 渲染产物
后端用 ECharts SSR（node-canvas 或 echarts-ssr）
生成 PNG 附件 + 文本摘要
失败时只发文本告警
↓
5. 推送渠道
邮件（SMTP）/ 飞书 webhook / 钉钉 webhook
失败重试 3 次，指数退避
↓
6. 记录投递结果
BiSubscriptionDelivery（投递日志）
更新 next_run_at（按 cron 计算）
数据模型
BiSubscription (新建)
├─ id, tenant_id, created_by
├─ name 订阅名称
├─ target_type chart/dashboard
├─ target_id 图表或看板 ID
├─ cron_expr cron 表达式
├─ channels_json 推送渠道列表
│  [{type:email,to:[...]},
│   {type:feishu,webhook:...},
│   {type:dingtalk,webhook:...}]
├─ filters_json 筛选器（同看板）
├─ status active/paused
├─ next_run_at 下次执行时间
└─ AuditMixin + SoftDeleteMixin
BiSubscriptionDelivery (新建，投递日志)
├─ id, subscription_id
├─ status success/failed
├─ error_msg
├─ row_count, elapsed_ms
├─ attachment_path PNG 路径
└─ delivered_at

关键设计决策（需你确认）

设计倾向

  • 调度引擎：复用 manifest 的 PeriodicTask（项目已有，每分钟触发 + leader_only）。不引入 Celery beat，保持架构一致
  • cron 表达式：标准 5 段式（分 时 日 月 周），前端用 cron-editor 可视化编辑器，避免用户手写
  • 图表渲染：后端 SSR 用 playwright headless 截图（复用项目已有的 ECharts 配置，保证与前端一致）。比 node-canvas + echarts-ssr 方案更准但更重，一期可先用"只发文本摘要 + CSV 附件"，PNG 截图作为二期
  • 推送渠道（一期）：邮件（SMTP，aiosmtplib）+ 飞书 webhook（httpx）。钉钉/企微二期
  • 失败处理：投递失败重试 3 次（指数退避 1/2/4 分钟），全失败后标记 failed 并通知订阅创建者
  • 时区：cron 按租户时区执行（tenant.timezone，默认 Asia/Shanghai），避免跨国企业时差问题
  • 与异步大查询的关系：定时任务触发时调 ② 的执行引擎，结果不落 BiQueryTask（直接走推送流程），但记录到 BiSubscriptionDelivery

风险/限制

  • playwright 截图较重（启动浏览器实例）→ 限制并发数（最多 2 个），超限排队
  • 邮件/飞书 webhook 凭证需加密存储 → 复用 BI_CRYPTO_KEY（Fernet）
  • cron 编辑器是新前端依赖 → 评估包大小
  • 时区配置依赖租户模型有 timezone 字段 → 当前无，需先加
  • 大结果推送：邮件附件限制 25MB，超限改为"下载链接"（7 天有效）

一期范围建议（降低风险）

一期做：订阅 CRUD + cron 调度 + 邮件推送（文本摘要 + CSV 附件）+ 飞书 webhook（文本卡片）+ 投递日志
二期做：PNG 截图推送（playwright SSR）+ 钉钉/企微 + 全局筛选器 + 失败告警通知创建者
